# Lua Bytes Views Implementation Plan

**Goal:** Add editable Lua bytes views backed by immutable memory/files, with explicit source replacement and bounded memory, excluding `to_hex`, Lua patterns, chunk iterators and delta spilling.

**Architecture:** A piece list shares immutable backing ranges; edits replace ranges with Lua-managed binary strings. Independent snapshots copy only range metadata. File reads and HTTP Asset writes use bounded buffers. Lua string functions implement pack/unpack semantics. Persistent HTTP replacements reuse Asset references; read-time redaction results use managed temporary files.

**Tech Stack:** Rust, mlua/Lua 5.4, existing tempfile, AssetStore and BodySource machinery.

- [x] Integrate `lua.rs`, `lua/codec.rs` and `lua/websocket.rs`: all agreed `as_bytes` entry points; Base64 and WS accept views; HTTP writes create Assets and retain existing replacement/history types. Verify source immutability and submission snapshots.
- [x] Integrate `lua/redaction.rs` and BodySource consumers: transactional binary HTTP output and file lifetime, existing WS size limit and original-read semantics. Verify large binary output and failed policy isolation.
- [x] Update `docs/lua-api.md`, `skills/proxycrab/` references, fixture and eval. Run relevant Rust tests and formatting/diff checks; inspect the final diff for scope and maintenance cost.

## Agreed limits

All bytes-accessible files are immutable. Large file views do not materialize the full source. Memory for edits/metadata/results is bounded by the sandbox budget; excess fails rather than spilling edits to disk. `find` is literal only. WS retains its 16 MiB limit. No source permissions change. Existing text/JSON getters retain their semantics. Preserve the user's existing `AGENTS.md` edit.
